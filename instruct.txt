一、项目简介
------------------------------------------------------------
一个安卓端“游戏创作 Agent”平台，底部三个 Tab：我的游戏、创作、设置。

1. “我的游戏（首页）”展示用户已经制作好的游戏，点击即可立即游玩；
   每张游戏卡片显示：游戏名、用户描述、更新时间，支持：重命名、继续对话编辑、删除、文件夹，
   有未保存草稿时显示“继续上次创作”入口。
   文件可视系统（只读概览，不提供打开文件功能）：游戏卡菜单“文件夹”进入 FileBrowserScreen，
   像资源管理器一样展示该游戏存储文件夹（filesDir/games/<id>）一级条目——
   名称、类型（文件夹/HTML 网页/JSON 数据/SHA-256 校验/版本标记/文本，.versions 标为版本归档文件夹）、
   大小（目录显示子项数）、修改日期（yyyy-MM-dd HH:mm）；子目录在前、其余按名称排序；
   数据来自 GameRepository.listGameFiles（GameFileEntry），页面无底部导航、返回即回首页。
2. “创作”页面可以用自然语言描述游戏（如“做一个打地鼠小游戏”），
   AI 即时生成 Android WebView 平台运行的单人游戏(HTML+CSS+JavaScript)，LLM SSE 流式输出（打字机效果）。
	- 交互形态类似豆包/元宝的对话 Agent：左侧 AI、右侧用户，生成中显示实时流。
	- Agent Loop 内置：意图识别、prompt工程、代码生成和校验、失败自动重试等功能，
	tool call有读写文件和结构(权限严格限制在该游戏文件夹内)，尽量保证生成代码可直接运行。
		- 用户点击发送输入的文本后，发送键改为停止键，可随时中断Agent Loop接着追加输入文本；
		  停止键动态显示本轮已运行时长（「停止 X分Y秒」每秒刷新；发送/确认/修复/再试一次起算，确认门等待不计入）
	- 用户随时中断生成后，玩家可选择直接尝试游玩(正常现象：可能运行错误)
	- 切换页面/对话时生成任务在 ViewModel 协程与全局 GameAgent 中继续运行，制作完成后可在 WebView 中立刻游玩。
		- 运行时 JS 报错会弹出覆盖层，可“让 AI 修复”；也可继续对话迭代（如“加连击计分”），修改基于上一个版本的游戏文件进行。
		- 编辑区/运行区独立：Agent 工具沙箱写”编辑区”（filesDir/agent/workspace/<会话>），已保存游戏目录为”运行区”
		  （filesDir/games/<id>）——编辑会话期间运行区文件不被写入（只同步会话簿记），
		  “保存”按钮把编辑区全部游戏文件（index.html 版本化 + scenarios.json 等）整体覆盖到运行区，
		  同时把会话上下文冻结为保存点（games/<id>/.savepoint，撤销锚点）；
		  “撤销”按钮（仅编辑已保存游戏的会话）为保存的逆操作：保存区文件覆盖编辑区、
		  上下文回滚到保存点——未保存的修改与其后的对话记录被丢弃（二次确认，不可恢复）；
		  旧版本保存的游戏无保存点：撤销时清空对话只留说明气泡（保存点缺失时上下文不可回放），
		  可用 scripts/migrate-savepoint.py（adb run-as 直写 .savepoint）为旧游戏补建保存点恢复精确撤销；
		  编辑对话的”立即游玩”预览编辑区最新版本（不入运行区）；重新进入编辑对话从编辑区续作（未保存修改不丢）。
		- 成品可保存到本地游戏库，每个游戏对应一个文件夹。
3. “设置”页面可选择 LLM 厂商模型并配置 API Key：
   DeepSeek / Kimi (Moonshot) / OpenAI / Anthropic Claude / 智谱 GLM / 小米 MiMo / MiniMax / OpenRouter / 自定义，
   支持修改 Base URL、模型名、系统提示词、模型思考能力开关（默认关闭），并可“测试连接”；模型名称可自由编辑并带服务商下拉（可选清单=ProviderPreset.models，首位即默认，手输清单外模型同样有效）；测试连接成功时前端提示固定为「✅连接成功」（不回显模型返回内容），失败显示原因摘要。
   页面最下方显示 版本号 + 软件编译时间（BUILD_TIME，构建时写入 BuildConfig）——
   用于确认设备上运行的构建版本（Android Studio Apply Changes 热更新不刷新系统安装时间，
   不能靠"应用信息"的安装时间判断版本新旧）。
   （注：Deepseek模型为deepseek-v4-flash和deepseek-v4-pro,已弃用deepseek-chat）

核心思路：游戏不是编译出来的，而是 AI 生成的文本 = 可运行产物（HTML+JS+CSS 文件组：
  index.html 唯一入口 + 相对路径引用的 js/css 辅助文件；平台加载前经 GameBundle 内联合并为
  自包含单页面，真机与沙箱共用同一合并管道），
运行期由 Android WebView（Chromium 内核）解释执行。无编译环节，生成即玩；
鸿蒙 ArkWeb 同为 Chromium 内核，双端可复用。

内置 JS 引擎库（3D/物理等重模块的平台注入方案，条件引入机制）：
- 引擎不要求模型手写重模块（3D 软渲染/物理模拟实测必然退化为伪 3D 或碰撞 bug）——
  平台在 APK assets/engines/ 内置五个引擎（全部 UMD 全局、版本锁定、已验证可内联无 </script 字面量）：
  three.min.js（r128，全局 THREE，~600KB）/ matter.min.js（0.20，全局 Matter，~83KB）/
  pixi.min.js（7.4，全局 PIXI，~456KB）/ cannon.min.js（0.6.2 UMD，全局 CANNON，~132KB；cannon-es 无 UMD 故取经典版）/
  tween.umd.js（21，全局 TWEEN，~35KB）；
- 声明协议：模型在 HTML <head> 写 <meta name="ww-engine" content="three,matter">（逗号分隔多个，仅此一行，无任何 <script src>）；
- 注入管道：AppContainer 为 HtmlEnhancer 接入 assets 引擎源码 provider（惰性读取+缓存），
  HtmlEnhancer 检测声明后在 <head> 注入引擎源码（置于视口修复/游戏脚本之前，幂等）——
  真实游戏页（GameScreen）与沙箱（AndroidSmokeTestRunner）共用同一 inject 管道，天然一致；
- 条件引入机制（GameEngines.allowedFor：维度×系统×档位裁决，提示词/校验/执行器三处同源）：
  three=3D 必须；matter=含物理系统必须；pixi=弹幕射击可选（同屏数百实体性能不足时）；
  cannon=3D+物理可选（真刚体需求；体素 AABB 手写更简）；tween=精品档可选（表现层补间）。
  提示词只"教"满足条件的引擎（GamePrompt.engineContract 按条件组装范式段：必选/可选措辞），
  GameValidator.validate(html, allowedEngines) 打回条件不符的声明（如贪吃蛇声明 matter）；
- 游戏文件保持文本自包含（js/css 多文件相对引用，运行前平台内联合并；二进制资源仍禁止），离线可玩承诺与外部资源禁令不变；
- 引擎准入条件：单文件无依赖（UMD）、版本锁定、真机与沙箱注入一致、提示词有使用范式；
  新增引擎 = GameEngines 注册表加一行 + assets 放文件 + 范式文案 + 单测。

二、Agent核心说明
*前端 LLM SSE 显示 Agent 状态（游戏识别中/游戏策划中/游戏生成中/游戏校验中/对话回复中等）
*UI 零错误细节纪律：用户只输入游戏需求、只关心进度与结果；消除 bug 是 Agent 的内部职责。
	阶段进度词允许出现轮次计数与简短术语（第 N 轮 / 文件名如 index.html / 工具名如 editfile / 冒烟测试 / 兼容模式 / function calling 等），
	生成轮阶段条结构为「第 N 轮 - 代码生成中（工具模式）：正在生成/修改 index.html」，流式接收中追加「已接收 N 字符」；
	但错误原文与 bug 细节（校验报错内容、stack、具体哪行什么变量）不得出现在任何用户可见文案中；
	错误细节只进入模型上下文（tool_result 反馈/遗留问题注入）与决策日志（decisionLog 的"失败详情"，不对用户展示）；
	用户可见文案只有三种：阶段进度（含轮次与术语）、成功结果（+试玩建议）、失败结果（进度已保留+重试/换模型建议，零细节）。
Agent处理message流程如下：
	**默认契约：一个对话框只制作一个游戏，不处理单对话框的多游戏需求。 Game Schema JSON 对话框级别全局唯一，后续修改即以此为基础。
	game_generated == false时(dev默认创建游戏)：
		message → 意图层 → 识别层 → 策划层 → 确认门 → prompt → Agent Loop → HTML+CSS+JS game
	game_generated == True时(dev默认修复或改进游戏)
		message → 意图层 → prompt → Agent Loop → HTML+CSS+JS game
	→ 意图层：(dev/chat 二分类；本地正则优先，置信度<0.8 时 Lite LLM 复核，LLM 自报置信度<0.6 视为不可联回落本地默认)
		分类器只回答一个问题：用户是否想让游戏发生变化
		dev:	创建/追加/改进/调整/修复游戏的一切诉求	file权限：read/write，可调用工具开发游戏文件, game_lock=true
			默认偏向 dev：dev 误判成 chat 会丢弃用户的开发请求（致命），chat 误判成 dev 只多一次识别层调用后回退聊天（温和）
		chat:	readonly，不改动任何外部文件，也不改变游戏特性变量，纯文本输出任务，直接 build prompt → LLM 然后输出文本
			system prompt 附当前会话 rolling summary 作只读上下文（解决"它能联机吗"答非所问；readonly 约束文件不约束上下文）
		修复快车道（不经文本分类，由会话状态推导）：已锚定游戏 且 lastError/lastErrorSignature 非空
			（成功回合会把 lastError 清空，非空即"存在未消化的运行时错误"）→ 跳过识别/策划/确认门直通 Agent Loop，
			指令以玩家本轮诉求为准（最小改动修复优先，不预设"功能特性不变"——玩家嘴里的异常可能实际是行为调整）
		（feature/bug 之分下推给策划层与 Agent Loop：它们看得到代码与用户诉求，判得更准；
		  new_game vs 迭代由会话级 Game Schema 是否为空判定，同样不靠分类）
	(区分feature和module，feature包含module，feature可小为一个按钮的样子或位置，module为游戏中某个系统模块例如)
	→ 识别层：
		检测 Game Schema JSON 会话级的游戏Json 是否为空：
			Json为空 → 对话历史不包含游戏 → 默认为首次 dev 对话
			Json非空 → 对话已经锚定某游戏
		正则 + Lite LLM 抽取游戏特征（除非用户说明，按该游戏类型的核心+标配系统集合识别），补全或修正 Game Schema JSON 信息
			（先过 JSON Schema +枚举白名单校验：方向/维度的同义写法先归一化——横屏/横版/landscape→横板、竖屏/portrait→竖版、
			  2d/二维→2D、伪3d→2.5D、三维→3D——归一化在 Lite LLM 解析出口与 validate 双侧生效；
			  不归一化时白名单会把 Lite LLM 常回的"横屏"静默映射成默认竖版，用户明确要横板却被翻成竖版；非法值仍映射默认值）
	 		若返回为空实体，则判断 message 为普通 chat （意图层可能误判漏判）
		解析实体包括：
			画面维度：2D，2.5D，3D
			画面方向：横板，竖版
			游戏系统：人物实体，道具，战斗，技能，属性等级，关卡场景，AI策略，商店经济等。
				(识别层事先定义较完整的游戏系统列表)
			参考对标游戏：市场内的某著名游戏或无，可辅助补全游戏特性。（映射到内部模板库template_id + 相似度，映射不上返回 template:null）
        例如"做一个2D版竖切面的我的世界游戏"：
			第一步检测对标游戏<我的世界> -> ["3D","竖版",[人物实体,道具,战斗]]
			第二步抽取游戏特性 -> ["2D","",[]] -> 键值修正 + 列表元素追加或删除
			得到 game_module_list 列表，初始化Game Schema JSON
	→ 策划层：
		策划子 Agent 拿到上游的系统列表 game_module_list，例如[人物实体,道具,战斗]，针对每个 module 元素策划出在这个游戏中合理的实现方式（业务验收边界）
		例如<我的世界>游戏的"人物实体" module，简单诠释其在游戏的核心实现方式：用户可操作移动，有对应坐标...等
		（不用策划出或和用户探讨具体的技术细节，例如游戏引擎，算法等底层技术或逻辑。这里只探讨游戏内容和玩法系统逻辑。）
		策划默认口径为"类型标配的完整可玩版本"：核心玩法闭环=P0；类型常见标配内容（多种单位/敌人、波次或关卡递进、升级成长、经济资源）=P1 一并纳入；仅锦上添花的打磨=P2（除非用户明确说明）。
		若收到确认门的修正文本：回到识别层在同一份 Game Schema 上补全/重组摘要，再次回显待确认；
		策划 LLM 延迟到玩家点击确认才执行（确认后的范围才是策划输入）——确认时对全部纳入系统统一定稿，
		取消勾选的 module 直接剔除（无 LLM 调用），不设独立的"只重策划变动项"路径
	→ 确认门：用卡片回显上游游戏JSON的综合策划结果，
		卡片中对于 game_module_list 的每个 module 都有一个可选框供用户勾选(默认为勾选，确认或取消勾选代表是否希望实现这个游戏系统)
		（勾选只做加法不做减法：勾选=纳入本轮实现范围；取消勾选=仅不纳入，不进任何禁止清单，后续文本点名该系统自动恢复；
		  excluded_systems 只包含用户文本明确说"不要"的系统——任何未勾选/未提及的系统都不做禁止，模型按用户原话与类型标配的完整可玩版本自行取舍；
		  全部不勾选=裸需求模式——不套用预设系统清单，等价于用户原话直接交给 Agent，
		  需要哪些玩法系统由模型按需求自行判断（类型标配完整可玩），照常进入 Agent Loop 不影响生成）
		系统清单末尾提供"全选"开关（TriStateCheckbox，一键全选/全不选，半选=部分勾选；全不选时显示裸需求模式提示）；
		其后为"质量档位"四挡单选（RadioButton 列表，默认 均衡）：快速（最快速度直出产品，不做任何测试）/
		轻量（一轮测试保证能运行成功）/均衡（保证运行成功＋检查基本功能正确）/精品（保证运行成功＋检查基本功能正确＋功能更丰富）；
		确认后写入会话 GameSession.qualityTier（fast/light/balanced/premium）并锁定进卡片；
		待确认期间输入文本修正时，当前档位随消息带回（sendUserMessage 携带 qualityTier）并继承到重组卡，选择不重置；
		用户可点击卡片中确认按钮或再次输入文本修改，
		若用户输入文本，判定为修正，可能增删module_list元素或修改某module的具体实现，则回到策划层重组摘要再次回显待确认，
		直到用户点击确认则进入下一步。保留卡片于聊天框，只disable勾选框和按钮功能即可
	→ 决策层：根据用户最后确认的完整信息(需要实现的系统以及对应实现方法，需要排除的系统和方案)，输出完整策划 Schema JSON
		按 template_class（画面维度×画面方向×主类型）选取特征矩阵（系统×默认参数），只做"选系统+覆盖参数"，不自由发明
	→ Prompt：根据用户最后确认的完整信息组成游戏内容提示文本加入system 提示词（工具模式：文件内容一律经工具写入，回复正文不出现代码）+ 上下文最小化：
		首次生成放参考模板；迭代放 rolling summary（"最新内容请通过 readfile 获取"），其余靠工具按需取
	→ Agent Loop：（bug 修复轮数不设上限，多轮属正常；仅无进展与运行验证环境异常两类非修复性退出；
	  输出零截断：不携带 max_tokens、工具观察与消息全量透传；网络层超时（连接30s/读静默12min/写60s）是死连接探测器
	  而非 LLM 时长限制——只要流上有字节就永不触发，触发后走自动重试不截断输出；整体时长不设限，停止键是用户侧唯一主动中断）
	主路径为工具模式（ReAct 循环）：LLM 请求携带 tools（listfiles/readfile/writefile/appendfile/editfile，沙箱严格限游戏工作区目录）
	readfile 整读自适应：千行级以内文件的切片请求直接整读返回（实测修复轮 60~70% 轮次耗在切片重读上，每片一次 LLM 往返），
	  真正的大文件（>1200 行）保留切片语义；工具描述与纪律提示同步要求"多区段一轮并行 readfile、修改一轮并行 editfile"
		写入策略与修改范围契约：
			writefile=整量写入（新建文件或彻底重写）；editfile=精确替换（修改首选：改动最小、最快、不回归未要求部分，可整段替换）；
			appendfile=末尾追加（新增代码段，无行数限制）；用哪个由模型按任务自行权衡，执行层不做策略门禁。
			修改范围契约（仅提示词层约束，无执行层检查/撤回——LLM 仍主动发挥时不拦截，用户以停止键/撤销兜底）：
			修复/改进轮（非首次创建轮）注入 SCOPE_FENCE_RULE——"根据用户指令精准优化改进游戏"：
			只改用户点名的游戏特征，未点名特性（数值/规则/布局/显示/文案/音效/命名）保持原样，即使改动"更好"也不做；
			首次创建轮与用户明确要求重做的回合不注入。
		无截断机制（彻底贯彻）：不捕获/不处理 finish_reason 截断信号；请求不携带 max_tokens（Anthropic 协议因 API 强制要求发送模型上限值），
		  工具观察（tool_result）与消息不做任何长度裁切——截断输出/裁切上下文只会制造非法工具参数与残缺代码；
		  模型输出体量由任务自然约束（首次生成体量大时允许 writefile 骨架 + appendfile 分段拼装）
			→ 模型发起 tool call → 宿主经 GameFileWorkspace 执行（版本化文件+指针切换+同会话加锁+hash防并发覆盖；
			  修改用 old_string 逐字符精确替换且要求唯一（或 replace_all），全量重写仅限首次生成或 overwrite=true 结构性重构）
			→ 每次写入后宿主自动检查产品契约（外部资源/eval 禁令，无解析器代差），报告作为"观察"附在 tool_result 回传
			→ 模型不再发起工具调用即自然终止；验收 = 产品契约通过 + 修改轮内容哈希≠种子哈希（防"空口完成"）+ 沙箱运行通过（均衡/精品档另含 scenarios.json 功能断言全通过）+ 可玩性自检轮全部完成
			→ 每次写入即刻发布中间版本到会话，中断后玩家可立即试玩
			→ 回合耗时回显：四类回合入口（发送消息/确认门确认/报障修复/再试一次）起算计时，回复结算附带"本轮耗时"——
			  成功回复为"（本次 Agent Loop 共 N 轮，耗时 X）"、聊天与失败回复为"（耗时 X/本轮耗时 X）"；
			  确认门等待用户思考不计入（确认点击重新起算）；耗时同时记入决策日志（elapsedMs 毫秒值）与 AgentLog
			→ 回合结构指标（跨游戏横向度量迭代健康度）：交付时决策日志追加"共 N 轮（readfile 调用 X 次占轮次 Y%）、
			  场景断言失败累计 Z 次、沙箱尝试 M 次"；readfile 占比 >50% 且轮数 ≥10 时标记"切片重读浪费轮次"——
			  用同一把尺子对比不同游戏的修复轮健康度，调优有据可依
	后台保活（前台服务，P0）：生成任务开始即启动 dataSync 前台服务 GenerationForegroundService——
	切后台/息屏不中断（前台服务豁免 Doze 网络限制 + partial wakelock 防 CPU 休眠导致 SSE 停摆）；
	通知内容为阶段进度（零技术细节纪律对通知同样成立，节流 ~1s），带"停止"动作（接 stopGeneration）；
	服务自行观察 isGenerating 收尾（完成/失败/确认门等待/用户停止均会翻 false），Agent 侧不主动 stop
	（避免上回合取消回调与下回合启动的竞态）；Android 15+ dataSync 6 小时上限由 onTimeout 退前台兜底（不终止生成）；
	通知权限（Android 13+）在 MainActivity 启动时请求，拒绝仅影响通知显示、不影响后台生成；
		服务同时持有 WifiLock（高性能模式）降低后台网卡省电断流；LLM 调用带网络韧性：网络/超时/5xx/真限流 429/overloaded
		自动重试最多 4 次（5/15/30/60s 递增退避，阶段显示"网络波动，正在自动重试"；后台瞬断恢复窗口常需 30~60s）；账户额度类（GLM 429+code1113 余额不足、
		DeepSeek 402 Insufficient Balance）与鉴权/模型类 4xx 不重试，如实提示"LLM 服务不可用"（余额/密钥/模型指引）——
		确定性失败不伪装成网络波动；后台瞬断不再直接判死整个回合；
		交付约束：交给用户前必须通过基础校验（0 error）、沙箱冒烟测试（同 WebView 内核确定性 tick 跑通）与两轮可玩性自检（内容完整性、体验与平台合规），不存在"带错交付"
	防死循环与交付约束：不做"带错交付"（交给用户前必须沙箱运行通过）——
		bug 修复轮数不设上限（多轮修复属正常现象，同错误 3/6 次仅注入"换思路/重写模块"提示，不终止）；
		仅两类非修复性退出熔断：无进展（连续24轮无任何文件修改 / 连续多轮无工具产出）与运行验证环境异常；
		用户停止键可随时中断（中断后保留中间版本可试玩，属用户主动选择）
			沙箱失败但无任何错误文本（探针结果不可读等设施问题）视为测试设施异常，以"运行验证环境异常"退出不交付——探针运行在 srcdoc iframe 内，结果经 contentWindow 读取
			超时语义：探针内部超时 45s/外层兜底 80s（模拟器/低端机 WebView 定时器慢 3~5 倍）；"超时且无任何真实错误文本"= 慢环境时序问题而非游戏缺陷，
			按通过交付并记决策日志——绝不作为可修错误回传（模型无从修起，只会无限空转）；超时伴随真实错误时只回传真实错误
	确认门与 Agent Loop 的关系（通用 Agent 流程，参考 DSH/ZaiAgent 形态）：
		卡片勾选与否只影响 prompt 构建（design_schema 内容），不影响后续 Agent Loop 流程——
		有勾选：勾选系统进入 design_schema 作为实现清单；无勾选（裸需求模式）：不套用预设系统清单，以用户原话为准；
		两种情况进入同一个 Agent Loop：生成完整游戏 → 沙箱运行 → 报错文本回传修复 → 循环直至沙箱通过交付
		协议层：OpenAI 兼容 delta.tool_calls 按 index 流式聚合（arguments 分片拼接）；Anthropic tool_use content block
			解析与 tool_result 回填（连续工具结果合并进同一 user 消息满足角色交替）；
			网关不支持 function calling（4xx 提及 tool/function）时去掉 tools 重试；
			工具失效降级：连续 2 轮既无工具调用也无代码输出（模型不支持/未启用 function calling，如实测 glm-5.3-flash）
			→ 整体降级为兼容回环——工具模式提示词禁止正文输出代码，会把这类模型锁死成"只能干聊"；
			兼容回环入口带 seedHash 防假修改闸：输出与种子完全一致时拒绝，要求输出包含修改的新版本
	校验体系（沙箱唯一裁决）：运行正确性的唯一校验来源是沙箱——同内核 WebView 直载探针注入后的游戏 HTML
		（不用 iframe/srcdoc——实测模拟器上 iframe 加载/结果读取链路不可靠，历史累计 200+ 次超时，且 srcdoc 的 opaque origin 引发跨源异常）；
		视口方向随 Game Schema：横板游戏按 640×360 横屏视口运行（竖版按 360×640），与真实游戏页的横屏呈现一致；
			探针跑帧捕获异常（24帧×50ms/帧≈1.2s游戏时间）+ 全局 error 监听（含事件回调）+ console error 采集 + 多点触控派发（中心/底部中央/左右下侧的 touchstart/touchend/click + 一次拖动，开始后与跑帧中段各一轮，让"开始"类交互真实触发并进入运行态）
			+ localStorage 内存 stub + 顶部平台按钮角落扫描（左上"返回"/右上"设置"各约 140×110px 悬浮区内出现 button/a/input 等可交互元素即判失败回传，平台自身 __ww 前缀元素除外；顶部其余区域可自由布局画面/HUD/文字，无保留区留白——提示词同口径约束角落避让）
			+ 画面方向与铺满断言（orientation-mismatch / canvas-not-fullscreen，跑沙箱的档位生效）：按 Game Schema 注入方向期望，
			  取面积最大的可见 canvas 为主画布，横板要求视觉宽>高、竖版要求高>宽（getBoundingClientRect 反映 transform 后视觉盒，
			  旋转画布实现同样正确判定）——拦"把关卡做成横向卷轴但画面仍是竖版"的假横板交付；同时断言主画布宽≥85% 视口宽、高≥60% 视口高
			  ——拦"固定逻辑分辨率+等比缩放居中"的黑边适配（宽屏左右大片空白）；无 canvas 的 DOM 游戏跳过（白屏检测兜底）
			+ restart() 契约检查（全档：全局 restart() 函数缺失即判失败回传；精品档 deep 模式额外真实调用 restart() 完整重开后复跑 12 帧，验证"完整重开"不抛错）
			+ 可观测性契约断言（全档）：生成契约要求游戏暴露 window.__wwDebugState() 状态快照
			  （静态校验先行检查函数存在），沙箱跑满帧后调用它做通用不变量检查——
			  负血量实体未移除（hp<0 应当帧移除）、数值 NaN/Infinity、活动实体超 500（泄漏）、
			  deep 重启后 state 仍为 over（重置不完整）——"不抛错但明显不对"的低级逻辑 bug 在交付前被客观拦截
			+ 功能断言/场景回归（均衡/精品档，GameScenario）：策划验收边界固化为可执行断言——
			  生成模型用 writefile 在工作区维护 scenarios.json（{"scenarios":[{id,system,name,steps,expect}]}，
			  最多 6 条/每条 12 步），expect 为针对 s（=__wwDebugState() 快照）的布尔表达式，
			  steps 为视口百分比输入脚本（tap/drag）+ 确定性帧推进（frames，每帧 50ms）；
			  主跑帧与不变量检查全绿后，探针在同一 finalize 调用内同步逐条执行：
			  restart() 重置 → 按 steps 派发输入 → 独立帧预算（≤40帧）推进 → 对快照求值断言；
			  失败以 scenario-fail[系统/名称]+实际快照（截断300字符）回传驱动修复（附"修逻辑还是对齐断言"引导）；
			  全部通过才放行——裁决权在确定性执行而非 LLM Critic（"LLM 提出，确定门裁决"）；
			  写 scenarios.json 时执行器即时做解析校验反馈（不发布 currentHtml、不跑 HTML 契约、不切入口指针）；
			  恒真式静态拒绝：expect 含 >=0（计数/长度天然非负）、!== undefined/null、typeof 判存在等近恒真子式时写入即打回（实测出现过 entities.length>=0 这类"写了等于没测"的断言）；
			  断言对齐路由：同一断言连续 3 次未通过时，反馈强制模型先做对齐判定——快照显示系统按验收行为运行则修断言（expect/steps）而非反复改游戏逻辑；
			  回归保护：文件持久化在游戏工作区跨迭代存活，修复玩家报障时把问题固化为新断言追加，
			  此后每次修改重跑全部断言，防"修好新问题弄坏旧功能"；档位缺失时一次性 nudge 补写（仅生成轮）；
			  套件上限 6 条：超限时提示合并同类或替换最弱断言（保留核心闭环与已修复缺陷条目）；
			  快速/轻量档不启用（快速不测试、轻量只保证可运行）；兼容降级回环（无文件工具）不适用
			+ 45s/80s 外层兜底（deep 60s/110s）；帧推进为宿主驱动：探针不自排程也不依赖任何页面事件/定时器
			  （离屏 WebView 的 DOMContentLoaded/setTimeout 可能被 Chromium 整体冻结），pump 每次实时读
			  document.readyState，宿主以 200ms 间隔轮询并每次调用 window.__wwPump(4) 推进 4 批帧
			  （后台 evaluateJavascript 回调延迟可达数百毫秒，多帧合并把往返次数从 24 降到 6：
			  24 帧约 1~4s、deep 约 2~6s）；轮询结果解析：evaluateJavascript 返回 JSON 编码字符串，
			  必须先按 JSON 字符串字面量解码再解析对象（直接 removeSurrounding 会因内层转义恒解析失败——
			  历史遗留 bug，曾经的"通过"全部是外层超时兜底假阳性）；帧跑满的同一批 pump 调用内直接落入
			  收尾检查（白屏/保留区/可观测性/restart），宿主在 f==24 的同次轮询即读到终态；
			  超时且零帧推进判"运行验证环境异常"不交付（不再按慢环境放行）；
			  沙箱瞬时故障自愈（防整轮全废）：活性早检——轮询 15s 宽限期后仍 frames=0 且 pump=0
			  （探针 JS 从未真正执行：renderer 冻结或页面卡在 loading）即提前终止本次尝试，不等 80s；
			  设施类失败（smoke-frozen/结果不可读/smoke-warmup/smoke-renderer-gone）由 runner 销毁重建 WebView 重试至多 2 次
			  （该故障间歇性发作，实测曾连续 5 回合在 LLM 工作完成后死在沙箱后自愈——新实例大概率落到健康 renderer）；
			  游戏自身错误（有错误文本/帧有推进）不重试；全部尝试耗尽才向上报"运行验证环境异常"；
			  WebView 用后即毁（根修复）：每次沙箱尝试与离开游戏页都 destroy 对应 WebView——不销毁会累积占用
			  共享渲染器的 tile 内存与 JS 堆（实测模拟器连续多轮后 chromium 报 tile memory limits exceeded，
			  新页面无法绘制→设施故障；"重启进程自愈"的根因即资源耗尽而非随机病态）；
			  预热门握手：载入真实页面前先在空白页执行最小 JS 回声（最多 10 次×0.5s），JS 桥无响应按可重试
			  设施失败快速重建，不消耗整轮外层超时；onRenderProcessGone（渲染器死亡官方信号）同样立即
			  按可重试设施失败终止重建；设施异常 internalDetail 携带失败 message 与尝试次数便于定位；
			  完成判定以探针定稿为准（window.__wwSmokeFinalized）：deep 复跑期间 framesRun 已达 24 但未定稿时
			  不得提前收单（历史竞态：读到 passed=false/errors=[] 中间态被判"结果不可读(smoke-failed)"设施异常，
			  精品档主阶段干净的运行必现，表现为 5 秒内失败且仅 1 次尝试）；
			  SmokeTestResult.attempts 记录总尝试次数（进 AgentLog 与决策日志结构指标）；
			画面空白检测（白屏杀手锏）：跑满帧后所有 canvas 均无内容（空白 canvas 的 PNG dataURL <3KB）且页面无可读文本 → 判"playability-blank-screen"失败回炉——杀掉"运行不报错但啥都没渲染"的假通过；
			可玩性自检轮（对标 DSH/ZaiAgent 的自检-增强流程）：沙箱通过后不立即交付，逐轮注入"对照【可玩性要求】自查修复"再验收——
			自检为有据自查：沙箱功能断言结果（X/Y 通过+清单）作为证据前缀注入自检提示，模型基于运行证据自查，不重复已被断言验证的内容（替代无执行依据的纯自我感觉）；
			轮数随质量档位（确认门四挡 qualityTier）与回合类型分档：
			生成轮——快速/轻量无自检（轻量仍跑沙箱保证可运行）、均衡一轮内容完整性（含基本功能正确与平台合规要点）、
			精品两轮（追加丰富度与打磨：内容量/数值平衡/视觉层次/音效层次）；快速档完全跳过沙箱（不做任何测试，玩家回传兜底）；
			均衡/精品档沙箱验收携带工作区 scenarios.json 功能断言一并执行（回归套件随修复持续累积）；
			修复轮（fixTurn：运行报错回传/修复快车道）——快速档无自检，其余档位仅一轮回归自检（验证修复达成诉求且未破坏既有内容），已有断言自动重跑作回归门；
			每轮完成后重新过校验+沙箱验收，当前档位全部轮次消费完才交付；
			档位同时经 GamePrompt.tierPrompt 注入生成上下文（快速=最简直出/轻量=最简可玩闭环/均衡=类型标配完整/精品=内容更丰富+打磨项）；
			精品档另有防敷衍增强：自检期间零修改直通时，一次性注入"丰富度增强"指令（防空口完成；工具模式与兼容降级模式均生效；仅生成轮触发，修复轮不触发——修 bug 时不应被要求扩内容）；
			能成功运行（跑满帧且零错误文本且画面非空白且左上/右上角平台按钮区无可交互元素）即放行；失败则以沙箱报错文本作为观察回传驱动修复；
			无任何 runner 可用（JVM 单测等）时跳过沙箱不阻塞；
			静态解析校验（Rhino 语法/no-undef/jsoup HTML 配对）已全部移除——解析器与 Chromium 存在语法代差，
			class/可选链/空值合并/spread/for-of/箭头默认参数等合法写法会被误判（实测 15 样本误判 7 个），
			模型照假报错去修只会烧轮次；语法错误的捕获交给沙箱（Chromium 自身即最好的解析器，SyntaxError 会出现在 console error）
			仅保留轻量产品契约检查（GameValidator，纯正则/标签枚举，无代差）：自包含（禁外部 CDN；本地 js/css 引用按工作区存在性裁决——
			  存在=合法多文件组织，缺失=error 引导先 writefile 创建；本地二进制图片/音频仍禁；并禁 ES module import/export），离线可玩承诺
			与安全禁令（eval/new Function/动态 require/import()）
		校验与交付五条保证：
			① 沙箱模拟用户环境：与真实游戏页（GameScreen）一致的 WebView 配置（JS/domStorage/wideViewport/overview）
			   + 视口 360×640（innerWidth/Height 非 0）+ JS 弹窗自动确认（alert/confirm/prompt 不挂起）+ HtmlEnhancer 同样注入
			② 沙箱运行成功才交付：设施异常（结果不可读/执行异常）也一律不交付，以"运行验证环境异常"理由退出；
			   仅 JVM 单测（无 runner）跳过沙箱

			④ bug 修复轮数不设上限：多轮修复属正常现象，同错误 3/6 次仅注入升级提示不终止
			⑤ Agent Loop 任何退出都有用户可见理由（零技术细节）：制作完成（可游玩）/ 网络或服务异常（检查网络与配置）/

VIEWPORT_PRELUDE（视口修复 + 平台设置桥接）：
- 用 window.__wwViewportFixApplied 防重复执行；
- 视口修复：取 window.innerHeight || documentElement.clientHeight，把
  <html>/<body> 的 height/minHeight 固定为像素高度；创建 <style id="__ww_vh_fix__">，
  遍历 document.styleSheets 中 type=1 的规则，把含 vh 的声明换算成 px 并以
  !important 追加；再遍历所有元素内联样式做同样的 vh→px 替换；
- 设置面板已上移平台顶栏：顶栏右侧“⚙ 设置”入口（替代原“保存”按钮）由原生 GameScreen 渲染，
  游戏页内不再注入任何设置按钮/面板；页面侧仅暴露两个接口供原生面板经 evaluateJavascript 调用：
  window.__wwSetVolume(v)（0–1）与 window.__wwSetPaused(bool)。
  原生“游戏设置”面板（AlertDialog）内容：音量滑条（实时 __wwSetVolume）、
  “重新游戏”（evaluateJavascript 调全局 restart()，失败转 console.error
  “[游戏错误] 重新游戏失败: …”）、“保存游戏”（仅草稿模式显示，转原有的标题确认保存流程）、
  “继续游戏”（关闭面板）；
- 暂停机制：包装 window.requestAnimationFrame/cancelAnimationFrame，
  __wwPaused=true 时持续重排下一帧而不回调游戏逻辑；原生设置面板打开即
  __wwSetPaused(true) 暂停，关闭/继续游戏恢复；
- 音量机制：默认 __wwVolume=0.8，__wwSetVolume 钳制 0–1.5（原生滑条 0–150%，
  允许对游戏自身偏小的音效做适度放大；参考模板 game_template.html 的音效振幅为 0.15）；
  包装 window.AudioContext/webkitAudioContext
  构造函数，为每个新 AudioContext 创建主 GainNode（__wwMasterGain），并 patch
  AudioNode.prototype.connect，把连接到 ctx.destination 的节点统一改接到主
  GainNode；__wwSetVolume 遍历已登记 Context 设置 gain.value；
- 自动清理：隐藏游戏自带的“重新开始/重开/重玩/再来一局/restart”按钮
  （display:none 并打 __wwLegacyRestartHidden 标记）；
  MutationObserver 监听 DOM 变化以重新执行按钮清理；
- 触发时机：DOMContentLoaded（或 readyState 非 loading 时立即执行）+ setTimeout 0
  兜底 + resize/orientationchange 重新计算。



七、构建与运行
------------------------------------------------------------
环境要求：JDK 17、Android SDK（路径见 local.properties 或 Android Studio SDK Manager）、
可用模拟器或真机（minSdk 26）。

常用命令（在项目根目录 D:\DATA\GitProjWorkSpace\GameWishingWell 下执行）：

    # 1. 编译 Debug APK
    gradlew.bat assembleDebug

    # 2. 运行单元测试
    gradlew.bat testDebugUnitTest

    # 3. 连接设备/模拟器后安装启动（默认 launch）
    gradlew.bat installDebug

    # 4. 直接 adb 安装
    adb install -r app\build\outputs\apk\debug\app-debug.apk

    # 5. Release APK（当前 release 关闭混淆）
    gradlew.bat assembleRelease

Debug APK 输出：app/build/outputs/apk/debug/app-debug.apk。
单元测试报告：app/build/reports/tests/testDebugUnitTest/index.html。

Android Studio 运行方式：
1. 用 D:\APP\AndroidStudio\bin 启动 Android Studio，打开本项目；
2. 等待 Gradle Sync 完成（若 SDK 路径不对，修改 local.properties 的 sdk.dir）；
3. 选择模拟器或真机，运行 app 配置。

首次使用：
1. 进入“设置”，选择服务商，填写 API Key（必要时改 Base URL / 模型）；
2. 点击“测试连接”确认可用；
3. 进入“创作”，用一句话描述游戏并发送；
4. 生成完成后“立即游玩”，或“保存”到“我的游戏”。

常见问题：
- 构建同步报 SDK/JDK 错误：检查 local.properties 与 JDK 17。
- 提示“请先在设置中配置 API Key、地址和模型”：isConfigured() 要求三项均非空。
- 模型输出为空或抽不到 HTML：检查模型/网关是否支持流式 chat/completions；
  DeepSeek 默认模型为 deepseek-v4-flash（deepseek-chat 已弃用），请求不携带 max_tokens（输出长度不设限）；
  思考能力由设置页开关控制（默认关闭）。
- 游戏白屏：确认生成 HTML 中 canvas 使用 vh/100% 也可渲染；HtmlEnhancer 已做视口修复，
  但模型仍应遵守“自包含（多文件仅限 js/css 文本）、无外部资源、引用文件真实存在”的提示词约束。
