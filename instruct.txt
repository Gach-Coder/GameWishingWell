一、项目简介
------------------------------------------------------------
一个安卓端“游戏创作 Agent”平台，底部三个 Tab：我的游戏、创作、设置。

1. “我的游戏（首页）”展示用户已经制作好的游戏，点击即可立即游玩；
   每张游戏卡片显示：游戏名、用户描述、更新时间，支持：重命名、继续对话编辑、删除，
   有未保存草稿时显示“继续上次创作”入口。
2. “创作”页面可以用自然语言描述游戏（如“做一个打地鼠小游戏”），
   AI 即时生成 Android WebView 平台运行的单人游戏(HTML+CSS+JavaScript)，LLM SSE 流式输出（打字机效果）。
	- 交互形态类似豆包/元宝的对话 Agent：左侧 AI、右侧用户，生成中显示实时流。
	- Agent Loop 内置：意图识别、prompt工程、代码生成和校验、失败自动重试等功能，
	tool call有读写文件和结构(权限严格限制在该游戏文件夹内)，尽量保证生成代码可直接运行。
	- 用户点击发送输入的文本后，发送键改为停止键，可随时中断Agent Loop接着追加输入文本
	- 用户随时中断生成后，玩家可选择直接尝试游玩(正常现象：可能运行错误)
	- 切换页面/对话时生成任务在 ViewModel 协程与全局 GameAgent 中继续运行，制作完成后可在 WebView 中立刻游玩。
	- 运行时 JS 报错会弹出覆盖层，可“让 AI 修复”；也可继续对话迭代（如“加连击计分”），修改基于上一个版本的游戏文件进行。
	- 成品可保存到本地游戏库，每个游戏对应一个文件夹。
3. “设置”页面可选择 LLM 厂商模型并配置 API Key：
   DeepSeek / Kimi (Moonshot) / OpenAI / Anthropic Claude / 智谱 GLM / 自定义，
   支持修改 Base URL、模型名、系统提示词、模型思考能力开关（默认关闭），并可“测试连接”。
   （注：Deepseek模型为deepseek-v4-flash和deepseek-v4-pro,已弃用deepseek-chat）

核心思路：游戏不是编译出来的，而是 AI 生成的文本 = 可运行产物（HTML 文件），
运行期由 Android WebView（Chromium 内核）解释执行。无编译环节，生成即玩；
鸿蒙 ArkWeb 同为 Chromium 内核，双端可复用。

二、Agent核心说明
*前端 LLM SSE 显示 Agent 状态（游戏识别中/游戏策划中/游戏生成中/游戏校验中/对话回复中等）
*UI 零错误细节纪律：用户只输入游戏需求、只关心进度与结果；消除 bug 是 Agent 的内部职责。
	阶段进度词允许出现轮次计数与简短术语（第 N 轮 / 工具名如 editfile / 冒烟测试 / 兼容模式 / function calling 等），
	但错误原文与 bug 细节（校验报错内容、stack、具体哪行什么变量）不得出现在任何用户可见文案中；
	错误细节只进入模型上下文（tool_result 反馈/遗留问题注入）与决策日志（decisionLog 的"失败详情"，不对用户展示）；
	用户可见文案只有三种：阶段进度（含轮次与术语）、成功结果（+试玩建议）、失败结果（进度已保留+重试/换模型建议，零细节）。
Agent处理message流程如下：
	**默认契约：一个对话框只制作一个游戏，不处理单对话框的多游戏需求。 Game Schema JSON 对话框级别全局唯一，后续修改即以此为基础。
	game_generated == false时(dev默认创建游戏)：
		message → 意图层 → 识别层 → 策划层 → 确认门 → prompt → Agent Loop → HTML+CSS+JS game
	game_generated == True时(dev默认修复或改进游戏)
		message → 意图层 → prompt → Agent Loop → HTML+CSS+JS game
	→ 意图层：(dev/chat 二分类；本地正则优先，置信度<0.8 时 Lite LLM 复核，LLM 自报置信度<0.6 视为不可联回落本地默认)
		分类器只回答一个问题：用户是否想让游戏发生变化
		dev:	创建/追加/改进/调整/修复游戏的一切诉求	file权限：read/write，可调用工具开发游戏文件, game_lock=true
			默认偏向 dev：dev 误判成 chat 会丢弃用户的开发请求（致命），chat 误判成 dev 只多一次识别层调用后回退聊天（温和）
		chat:	readonly，不改动任何外部文件，也不改变游戏特性变量，纯文本输出任务，直接 build prompt → LLM 然后输出文本
			system prompt 附当前会话 rolling summary 作只读上下文（解决"它能联机吗"答非所问；readonly 约束文件不约束上下文）
		修复快车道（不经文本分类，由会话状态推导）：已锚定游戏 且 lastError/lastErrorSignature 非空
			（成功回合会把 lastError 清空，非空即"存在未消化的运行时错误"）→ 跳过识别/策划/确认门直通 Agent Loop，
			指令以玩家本轮诉求为准（最小改动修复优先，不预设"功能特性不变"——玩家嘴里的异常可能实际是行为调整）
		（feature/bug 之分下推给策划层与 Agent Loop：它们看得到代码与用户诉求，判得更准；
		  new_game vs 迭代由会话级 Game Schema 是否为空判定，同样不靠分类）
	(区分feature和module，feature包含module，feature可小为一个按钮的样子或位置，module为游戏中某个系统模块例如)
	→ 识别层：
		检测 Game Schema JSON 会话级的游戏Json 是否为空：
			Json为空 → 对话历史不包含游戏 → 默认为首次 dev 对话
			Json非空 → 对话已经锚定某游戏 
		正则 + Lite LLM 抽取游戏特征（除非用户说明，游戏系统默认为可玩的最简洁版本），补全或修正 Game Schema JSON 信息（先过 JSON Schema +枚举白名单校验，非法值拒绝或映射默认值）
	 		若返回为空实体，则判断 message 为普通 chat （意图层可能误判漏判）
		解析实体包括：
			画面维度：2D，2.5D，3D
			画面方向：横板，竖版
			游戏系统：人物实体，道具，战斗，技能，属性等级，关卡场景，AI策略，商店经济等。
				(识别层事先定义较完整的游戏系统列表)
			参考对标游戏：市场内的某著名游戏或无，可辅助补全游戏特性。（映射到内部模板库template_id + 相似度，映射不上返回 template:null）
        例如"做一个2D版竖切面的我的世界游戏"：
			第一步检测对标游戏<我的世界> -> ["3D","竖版",[人物实体,道具,战斗]]
			第二步抽取游戏特性 -> ["2D","",[]] -> 键值修正 + 列表元素追加或删除
			得到 game_module_list 列表，初始化Game Schema JSON
	→ 策划层：
		策划子 Agent 拿到上游的系统列表 game_module_list，例如[人物实体,道具,战斗]，针对每个 module 元素策划出在这个游戏中合理的实现方式（业务验收边界）
		例如<我的世界>游戏的"人物实体" module，简单诠释其在游戏的核心实现方式：用户可操作移动，有对应坐标...等
		（不用策划出或和用户探讨具体的技术细节，例如游戏引擎，算法等底层技术或逻辑。这里只探讨游戏内容和玩法系统逻辑。）
		若收到确认门的重组
			追加或修改 module —> 策划子 Agent LLM 重新策划该module
			删除 module -> 直接删除，无LLM调用
	→ 确认门：用卡片回显上游游戏JSON的综合策划结果，
		卡片中对于 game_module_list 的每个 module 都有一个可选框供用户勾选(默认为勾选，确认或取消勾选代表是否希望实现这个游戏系统)
		（勾选只做加法不做减法：勾选=纳入本轮实现范围；取消勾选=仅不纳入，不进任何禁止清单，后续文本点名该系统自动恢复；
		  excluded_systems 只包含用户文本明确说"不要"的系统——任何未勾选/未提及的系统都不做禁止，模型按用户原话与最简可玩原则自行取舍；
		  全部不勾选=裸需求模式——不套用预设系统清单，等价于用户原话直接交给 Agent，
		  需要哪些玩法系统由模型按需求自行判断（最简可玩），照常进入 Agent Loop 不影响生成）
		用户可点击卡片中确认按钮或再次输入文本修改，
		若用户输入文本，判定为修正，可能增删module_list元素或修改某module的具体实现，则回到策划层重组摘要再次回显待确认，
		直到用户点击确认则进入下一步。保留卡片于聊天框，只disable勾选框和按钮功能即可
	→ 决策层：根据用户最后确认的完整信息(需要实现的系统以及对应实现方法，需要排除的系统和方案)，输出完整策划 Schema JSON
		按 template_class（画面维度×画面方向×主类型）选取特征矩阵（系统×默认参数），只做"选系统+覆盖参数"，不自由发明
	→ Prompt：根据用户最后确认的完整信息组成游戏内容提示文本加入system 提示词（工具模式：文件内容一律经工具写入，回复正文不出现代码）+ 上下文最小化：
		首次生成放参考模板；迭代放 rolling summary（"最新内容请通过 readfile 获取"），其余靠工具按需取
	→ Agent Loop：（硬上限防死循环：工具模式总轮次40 / 兼容模式15 / 同一错误签名连续10 / 连续24轮无文件修改，任一超限即如实失败终止并保留中间版本；网络层连接30s/读5min/写60s超时防蜂窝NAT死连接）
		主路径为工具模式（ReAct 循环）：LLM 请求携带 tools（listfiles/readfile/writefile/editfile，沙箱严格限游戏工作区目录）
			→ 模型发起 tool call → 宿主经 GameFileWorkspace 执行（版本化文件+指针切换+同会话加锁+hash防并发覆盖；
			  修改用 old_string 逐字符精确替换且要求唯一（或 replace_all），全量重写仅限首次生成或 overwrite=true 结构性重构）
			→ 每次写入后宿主自动跑基础校验器，结构化报告作为"观察"附在 tool_result 回传（校验是观察不是门，模型自己决定怎么修）
			→ 模型不再发起工具调用即自然终止；修改轮验收要求最终内容哈希≠种子哈希（防"不做任何修改就宣称完成"的假成功）
			→ 每次写入即刻发布中间版本到会话，中断后玩家可立即试玩
		交付约束：交给用户前必须通过基础校验（0 error）与沙箱冒烟测试（同 WebView 内核确定性 tick 跑通），不存在"带错交付"
		防死循环与交付约束：不做"带错交付"（交给用户前必须通过基础校验0 error与沙箱冒烟），但设有硬上限——
			同一错误签名连续3次注入"换思路"提示、连续6次起强制"重写问题模块/换实现"（同签名次数写入阶段条供用户判断是否卡死）；
			同一错误签名连续10次、总轮次40（工具模式）/15（兼容模式）、连续24轮无文件修改，任一触发即如实失败终止并保留最新中间版本（可试玩，属主动止损而非交付）；
			熔断签名语义：按"单条错误"追踪（签名=类别+错误消息原文，保留变量名等标识符、不含行号），同一条错误连续N轮未被修掉才计数；
			错误集合的其它变化（修好一条/新增一条）不清零顽固项的连续计数——聚合式整集合比较会把"修好A新增B、C始终没修"误判为进展而漏熔断，标识符归一化会把不同变量的同类错误合并误熔断，均已规避
			用户停止键可随时中断（中断后保留中间版本可试玩，属用户主动选择）
			冒烟测试失败但无任何错误信息（探针结果不可读等设施问题）视为测试设施异常，跳过冒烟不阻塞交付——探针运行在 srcdoc iframe 内，结果经 contentWindow 读取
		协议层：OpenAI 兼容 delta.tool_calls 按 index 流式聚合（arguments 分片拼接）；Anthropic tool_use content block
			解析与 tool_result 回填（连续工具结果合并进同一 user 消息满足角色交替）；
			网关不支持 function calling（4xx 提及 tool/function）时去掉 tools 重试，模型首轮在正文直接输出整份 HTML 时
			自动降级为"全量重写→抽取→校验→文本反馈"回环（每轮重建 prompt 不累积历史，保留为兼容模式）
		生成代码契约：无 eval、无动态require、浏览器全局白名单、声明前置；
		校验用现成解析器（Rhino AST 做 acorn 同等的语法检查+no-undef 作用域链 + jsoup 做 htmlparser2 同等 HTML 配对 + 资源自包含检查），不自写 HTML 配对/作用域检查
		→ 基本校验(可正确运行测试)
			语法和基本逻辑校验，得到可运行的功能基本正确的游戏，校验成功后退出Agent Loop。
	→ HTML+CSS+JS game
		game_generated = True
	→（用户进入游戏测试和游玩）
		→ 运行时报错（格式化回传：file:line + stack + console 片段）再回到Agent Loop 修复
		→ 运行无报错，用户可选择输入文本改进游戏或报告缺陷，则回到Agent Loop 修复
		→ 更新 GameSession 并持久化（代码 + rolling summary：
			文件清单、设计Schema、known-issues、上次改进对应的缺陷、 决策 log（为什么这么改）+ 
			schema_version + 每通过校验的版本打快照（可回滚）+ 增量持久化（只存变更文件））

VIEWPORT_PRELUDE（视口修复 + 游戏内设置面板）：
- 用 window.__wwViewportFixApplied 防重复执行；
- 视口修复：取 window.innerHeight || documentElement.clientHeight，把
  <html>/<body> 的 height/minHeight 固定为像素高度；创建 <style id="__ww_vh_fix__">，
  遍历 document.styleSheets 中 type=1 的规则，把含 vh 的声明换算成 px 并以
  !important 追加；再遍历所有元素内联样式做同样的 vh→px 替换；
- 设置面板：固定右上角“⚙”按钮（top:112px/right:12px，z-index 99990）→
  全屏半透明 overlay（z-index 99999）→“游戏设置”面板：
  音量 range（0–100）、“重新游戏”（调用全局 restart()，失败转 console.error
  “[游戏错误] 重新游戏失败: …”）、“继续游戏”（关闭面板）；
- 暂停机制：包装 window.requestAnimationFrame/cancelAnimationFrame，
  __wwPaused=true 时持续重排下一帧而不回调游戏逻辑；打开设置面板即暂停，关闭恢复；
- 音量机制：默认 __wwVolume=0.8；包装 window.AudioContext/webkitAudioContext
  构造函数，为每个新 AudioContext 创建主 GainNode（__wwMasterGain），并 patch
  AudioNode.prototype.connect，把连接到 ctx.destination 的节点统一改接到主
  GainNode；__wwSetVolume 遍历已登记 Context 设置 gain.value；
- 自动清理：隐藏游戏自带的“重新开始/重开/重玩/再来一局/restart”按钮
  （display:none 并打 __wwLegacyRestartHidden 标记，不隐藏平台设置按钮）；
  MutationObserver 监听 DOM 变化以重新执行按钮清理和面板安装；
- 触发时机：DOMContentLoaded（或 readyState 非 loading 时立即执行）+ setTimeout 0
  兜底 + resize/orientationchange 重新计算。



七、构建与运行
------------------------------------------------------------
环境要求：JDK 17、Android SDK（路径见 local.properties 或 Android Studio SDK Manager）、
可用模拟器或真机（minSdk 26）。

常用命令（在项目根目录 D:\DATA\GitProjWorkSpace\GameWishingWell 下执行）：

    # 1. 编译 Debug APK
    gradlew.bat assembleDebug

    # 2. 运行单元测试
    gradlew.bat testDebugUnitTest

    # 3. 连接设备/模拟器后安装启动（默认 launch）
    gradlew.bat installDebug

    # 4. 直接 adb 安装
    adb install -r app\build\outputs\apk\debug\app-debug.apk

    # 5. Release APK（当前 release 关闭混淆）
    gradlew.bat assembleRelease

Debug APK 输出：app/build/outputs/apk/debug/app-debug.apk。
单元测试报告：app/build/reports/tests/testDebugUnitTest/index.html。

Android Studio 运行方式：
1. 用 D:\APP\AndroidStudio\bin 启动 Android Studio，打开本项目；
2. 等待 Gradle Sync 完成（若 SDK 路径不对，修改 local.properties 的 sdk.dir）；
3. 选择模拟器或真机，运行 app 配置。

首次使用：
1. 进入“设置”，选择服务商，填写 API Key（必要时改 Base URL / 模型）；
2. 点击“测试连接”确认可用；
3. 进入“创作”，用一句话描述游戏并发送；
4. 生成完成后“立即游玩”，或“保存”到“我的游戏”。

常见问题：
- 构建同步报 SDK/JDK 错误：检查 local.properties 与 JDK 17。
- 提示“请先在设置中配置 API Key、地址和模型”：isConfigured() 要求三项均非空。
- 模型输出为空或抽不到 HTML：检查模型/网关是否支持流式 chat/completions；
  DeepSeek 默认模型为 deepseek-v4-flash（deepseek-chat 已弃用），max_tokens 16384；
  思考能力由设置页开关控制（默认关闭）。
- 游戏白屏：确认生成 HTML 中 canvas 使用 vh/100% 也可渲染；HtmlEnhancer 已做视口修复，
  但模型仍应遵守“自包含、无外部资源”的提示词约束。
