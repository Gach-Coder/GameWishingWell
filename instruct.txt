一、项目简介
------------------------------------------------------------
一个安卓端“游戏创作 Agent”平台，底部三个 Tab：我的游戏、创作、设置。

1. “我的游戏（首页）”展示用户已经制作好的游戏，点击即可立即游玩；
   每张游戏卡片显示：游戏名、用户描述、更新时间，支持：重命名、继续对话编辑、删除，
   有未保存草稿时显示“继续上次创作”入口。
2. “创作”页面可以用自然语言描述游戏（如“做一个打地鼠小游戏”），
   AI 即时生成 Android WebView 平台运行的单人游戏(HTML+CSS+JavaScript)，LLM SSE 流式输出（打字机效果）。
	- 交互形态类似豆包/元宝的对话 Agent：左侧 AI、右侧用户，生成中显示实时流。
	- Agent Loop 内置：意图识别、prompt工程、代码生成和校验、失败自动重试等功能，
	tool call有读写文件和结构(权限严格限制在该游戏文件夹内)，尽量保证生成代码可直接运行。
	- 用户点击发送输入的文本后，发送键改为停止键，可随时中断Agent Loop接着追加输入文本
	- 用户随时中断生成后，玩家可选择直接尝试游玩(正常现象：可能运行错误)
	- 切换页面/对话时生成任务在 ViewModel 协程与全局 GameAgent 中继续运行，制作完成后可在 WebView 中立刻游玩。
	- 运行时 JS 报错会弹出覆盖层，可“让 AI 修复”；也可继续对话迭代（如“加连击计分”），修改基于上一个版本的游戏文件进行。
	- 成品可保存到本地游戏库，每个游戏对应一个文件夹。
3. “设置”页面可选择 LLM 厂商模型并配置 API Key：
   DeepSeek / Kimi (Moonshot) / OpenAI / Anthropic Claude / 自定义，
   支持修改 Base URL、模型名、系统提示词，并可“测试连接”。
   （注：Deepseek模型为deepseek-v4-flash和deepseek-v4-pro,已弃用deepseek-chat）

核心思路：游戏不是编译出来的，而是 AI 生成的文本 = 可运行产物（HTML 文件），
运行期由 Android WebView（Chromium 内核）解释执行。无编译环节，生成即玩；
鸿蒙 ArkWeb 同为 Chromium 内核，双端可复用。

二、Agent核心说明
前端 LLM SSE 显示 Agent 状态（游戏识别中/游戏策划中/游戏生成中/游戏校验中/对话回复中等），将代码生成时前端显示的固定文本(Agent Loop:意图识别 -> 策划 -> 生成 -> 校验 -> 冒烟测试)改为
Agent处理message流程如下：
	→ 意图层：(new_game/modify_game/chat)
		正则 + Lite LLM 抽取游戏特征，输出 Intent Schema JSON（先过 JSON Schema +枚举白名单校验，非法值拒绝或映射默认值
		解析实体包括：
			画面维度：2D，2.5D，3D
			画面方向：横板，竖版
			游戏系统：人物实体，道具，战斗，技能，属性等级，关卡场景，AI策略，商店经济等。
				(意图层事先定义较完整的游戏系统列表)
			参考对标游戏：市场内的某著名游戏或无，可辅助补全游戏特性。（映射到内部模板库template_id + 相似度，映射不上返回 template:null）
            （保留扩展位置）
		确认门：意图抽取完成后先以人话摘要回显识别结果（画面维度 / 方向 / 游戏系统 / 对标游戏特性默认值假设），逐一向玩家简单解释游戏计划包括那些系统以及具体将怎样实现这些系统（业务验收边界），
			用户可点击卡片中确认按钮或再次输入文本修改，若用户修正则重组摘要再次回显待确认，直到用户点击确认则进入下一步，确保已经获取用户全部需求；
			例如黄金矿工-道具系统：黄金/石头/炸弹，拾取判定为钩子触碰道具。
	→ 策划层：根据用户最后确认的完整信息(需要实现的系统以及对应实现方法，需要排除的系统和方案)，输出完整策划 Schema JSON
		按 template_class（画面维度×画面方向×主类型）选取特征矩阵（系统×默认参数），只做"选系统+覆盖参数"，不自由发明
		定稿 P0/P1/P2 特性分层 + 验收标准清单（供自检对照，防止确认偏差）+复杂度/资源预算（预估行数/脚本数）
		对于复杂的系统，代码层先隔离实现、优先校验
		策划重做上限 2 轮，回炉时喂入错误签名 + P0清单，避免重复产出同样范围
	→ Prompt：system 提示词 + 用户指令/策划 Schema 上下文最小化：
		只放 rolling summary + 本次要动的文件内容，其余靠readfile按需取）
	→ Agent Loop：
		→ 先出文件计划和依赖顺序（plan）→ implement → validate，中途不换文件切分方案
		→ tool call readfile/writefile 读/写已有的源码文件(HTML+CSS+JS)
			写入用版本化文件 + 指针切换（或OPFS），替代临时文件+rename；同会话加锁 / 文件 hash校验防并发覆盖
			修改已有文件用行级 patch，全量重写仅限首次生成
			生成代码契约：无 eval、无动态require、浏览器全局白名单、声明前置；
			校验用现成解析器（acorn 语法检查 + htmlparser2 HTML 配对 + eslint no-undef 规则），不自写 HTML 配对/作用域检查
		→ 基本校验(
			封装 validate 脚本，输出结构化 JSON {checks:[{category,file,line,message,severity}]}：
				语法：acorn 解析（JS/WASM）
				HTML 标签配对
				JS 引用的 DOM id 存在性（区分运行时动态创建的 id 白名单）
				静态运行时：引用未定义变量 / 函数
				资源缺失：引用的图片 / 音频不存在
				占位实现：TODO 标记 / 定义了但从未被调用的系统)
		→ 冒烟测试（同 WebView 内隔离 iframe 加载生成的 game 实际跑几帧：
			确定性 tick + 错误捕获 + 超时防定时器失控，替代 jsdom/Playwright；仅在静态校验全过后跑）
		→ 失败自动重试（按错误分类+预算，预算记账持久化进 GameSession，跨会话不重置：
			记账按"每次用户请求（回合）"计，错误签名库跨会话仅用于识别"同一错误"、不消耗预算：
			语法错≤3次 / 静态运行时错≤3次 / 用户回传运行时错≤3次 / 设计范围错回策划层重做范围（≤2轮）
			"同一错误"用规范化签名哈希判定（file:line + message正则化，行号漂移不影响匹配）
			超预算降级发 P0-only 版本：确定性裁剪 P1/P2，保留 P0 机制，资产换占位符）
		→ 自检：对照验收标准清单过一遍再宣布完成两段式：
			(a)验收标准对照（必读校验结果，已发现的错不得翻案）
			(b)代码质量检查输出结构化 verdict {pass, fails:[{item,severity}], note}
		→ 更新 GameSession 并持久化（代码 + rolling summary：
			文件清单、设计Schema、known-issues、上次错误、 决策 log（为什么这么改）+ 
			schema_version + 每通过校验的版本打快照（可回滚）+ 增量持久化（只存变更文件））
	→ HTML+CSS+JS game
	→ 运行时报错（格式化回传：file:line + stack + console 片段）再回到Agent Loop 修复（同一错误重复2次直接降级，不重复修）

VIEWPORT_PRELUDE（视口修复 + 游戏内设置面板）：
- 用 window.__wwViewportFixApplied 防重复执行；
- 视口修复：取 window.innerHeight || documentElement.clientHeight，把
  <html>/<body> 的 height/minHeight 固定为像素高度；创建 <style id="__ww_vh_fix__">，
  遍历 document.styleSheets 中 type=1 的规则，把含 vh 的声明换算成 px 并以
  !important 追加；再遍历所有元素内联样式做同样的 vh→px 替换；
- 设置面板：固定右上角“⚙”按钮（top:112px/right:12px，z-index 99990）→
  全屏半透明 overlay（z-index 99999）→“游戏设置”面板：
  音量 range（0–100）、“重新游戏”（调用全局 restart()，失败转 console.error
  “[游戏错误] 重新游戏失败: …”）、“继续游戏”（关闭面板）；
- 暂停机制：包装 window.requestAnimationFrame/cancelAnimationFrame，
  __wwPaused=true 时持续重排下一帧而不回调游戏逻辑；打开设置面板即暂停，关闭恢复；
- 音量机制：默认 __wwVolume=0.8；包装 window.AudioContext/webkitAudioContext
  构造函数，为每个新 AudioContext 创建主 GainNode（__wwMasterGain），并 patch
  AudioNode.prototype.connect，把连接到 ctx.destination 的节点统一改接到主
  GainNode；__wwSetVolume 遍历已登记 Context 设置 gain.value；
- 自动清理：隐藏游戏自带的“重新开始/重开/重玩/再来一局/restart”按钮
  （display:none 并打 __wwLegacyRestartHidden 标记，不隐藏平台设置按钮）；
  MutationObserver 监听 DOM 变化以重新执行按钮清理和面板安装；
- 触发时机：DOMContentLoaded（或 readyState 非 loading 时立即执行）+ setTimeout 0
  兜底 + resize/orientationchange 重新计算。



七、构建与运行
------------------------------------------------------------
环境要求：JDK 17、Android SDK（路径见 local.properties 或 Android Studio SDK Manager）、
可用模拟器或真机（minSdk 26）。

常用命令（在项目根目录 D:\DATA\GitProjWorkSpace\GameWishingWell 下执行）：

    # 1. 编译 Debug APK
    gradlew.bat assembleDebug

    # 2. 运行单元测试
    gradlew.bat testDebugUnitTest

    # 3. 连接设备/模拟器后安装启动（默认 launch）
    gradlew.bat installDebug

    # 4. 直接 adb 安装
    adb install -r app\build\outputs\apk\debug\app-debug.apk

    # 5. Release APK（当前 release 关闭混淆）
    gradlew.bat assembleRelease

Debug APK 输出：app/build/outputs/apk/debug/app-debug.apk。
单元测试报告：app/build/reports/tests/testDebugUnitTest/index.html。

Android Studio 运行方式：
1. 用 D:\APP\AndroidStudio\bin 启动 Android Studio，打开本项目；
2. 等待 Gradle Sync 完成（若 SDK 路径不对，修改 local.properties 的 sdk.dir）；
3. 选择模拟器或真机，运行 app 配置。

首次使用：
1. 进入“设置”，选择服务商，填写 API Key（必要时改 Base URL / 模型）；
2. 点击“测试连接”确认可用；
3. 进入“创作”，用一句话描述游戏并发送；
4. 生成完成后“立即游玩”，或“保存”到“我的游戏”。

常见问题：
- 构建同步报 SDK/JDK 错误：检查 local.properties 与 JDK 17。
- 提示“请先在设置中配置 API Key、地址和模型”：isConfigured() 要求三项均非空。
- 模型输出为空或抽不到 HTML：检查模型/网关是否支持流式 chat/completions；
